# CREDIT_POLICY.md — сервис кредитной политики (скоринг): требования и правила реализации

Инструкция для реализации. Формат и конвенции — как в MICROLOANS.md и CREDIT_BUREAU.md.
Ветка: `feature/credit-policy`. Три части работы:

- **Часть A — монолит** (`backend/`): только то, без чего нельзя, потому что монолит — хозяин заявки:
  новые поля профиля, статус `OVERDUE`, запрос скоринга и приём результата, запрет одобрения без скоринга.
- **Часть B — микросервис** `credit-policy/` (корень репозитория): правила, расчёт,
  чёрный список, журнал расчётов, админский API.
- **Часть C — бюро** (`credit-bureau/`): просрочка видна банкам.

Монолит в будущем будет разрезан на сервисы, поэтому всё, что относится к риску, живёт в `credit-policy`,
а не в монолите.

---

## 1. Зачем сервис

- Отсекает очевидные отказы без человека: админ не тратит время на заявки, которые всё равно отклонит.
- Одинаковые правила для всех: решение не зависит от настроения админа.
- Админ видит класс, вероятность дефолта и расшифровку по факторам и сортирует очередь по ним.
- Правила риска меняются независимо от остального кода и версионируются.

Расчёт выполняется один раз на каждую заявку (плюс повтор по кнопке админа).

## 2. Термины

| Термин | Значение |
|---|---|
| Фактор | Признак заёмщика, дающий балл от 0 до 1: история, цель, возраст, город, пол |
| score | Итог от 0 до 1: средневзвешенное баллов факторов |
| Скорбалл (points) | `round(score × 400)`, шкала 0–400, как у Нацбанка |
| Класс | A1 … E3 по скорбаллу; F — стоп-фактор, скорбалл не считается |
| PD | Probability of Default: прогноз вероятности невозврата, % |
| Стоп-фактор | Условие, при котором отказ без расчёта баллов: возраст вне 18–90, чёрный список, текущая просрочка |
| Решение | `RECOMMEND` — к админу с рекомендацией одобрить; `REVIEW` — к админу, высокий риск; `AUTO_REJECT` — отказ системой |
| Версия правил | Номер набора весов, баллов и порогов, по которому посчитан результат |

## 3. Модель

Модель **экспертная**, не статистическая: веса заданы людьми, а не выведены из данных. Когда накопится
статистика просрочек (статус `OVERDUE`), калибровку PD подбираем логистической регрессией на реальных данных.

### 3.1 Алгоритм

```
1. Стоп-факторы (собираются все сразу) → класс F, AUTO_REJECT, баллы не считаются:
   возраст вне [18, 90] (AGE_OUT_OF_RANGE), активный чёрный список (BLACKLISTED),
   заём в статусе OVERDUE (CURRENT_OVERDUE)
2. Нет даты рождения, пола, страны или города        → NOT_CALCULATED (MISSING_PROFILE_DATA), решение REVIEW
3. У типа займа нет балла цели (или он вне 0–1)       → NOT_CALCULATED (PURPOSE_SCORE_MISSING), решение REVIEW
4. score  = Σ (вес_i × балл_i) / Σ вес_i             (4 знака, HALF_UP)
   points = round(score × 400)                       (HALF_UP)
   класс  = по таблице §3.4
   PD     = 1 / (1 + e^(a + b × score))              (6 знаков)
   решение: points ≤ 125 → AUTO_REJECT; 125 < points ≤ 200 → REVIEW; points > 200 → RECOMMEND
```

Стоп-факторы проверяются раньше полноты данных: должник из чёрного списка получает отказ, даже если
у него старый неполный профиль.

Возраст считается на дату расчёта в поясе `Europe/Minsk`, полных лет.

### 3.2 Веса и баллы — версия правил 1

| Фактор | Вес | Значение → балл |
|---|---|---|
| История | 0.30 | §3.3 |
| Цель | 0.20 | балл цели у типа займа в монолите (`loan_types.purpose_score`, §7.3) |
| Возраст | 0.20 | 18–39 → 0.3; **40–60 → 0.5** (максимум); 61–90 → 0.4. Границы 40 и 60 включены в средний диапазон |
| Город | 0.15 | Минск 0.9; Гомель 0.2; прочие города Беларуси 0.15; другие страны 0.5 |
| Пол | 0.15 | женщина 1.0; мужчина 0.6 |

Город сравнивается после нормализации: нижний регистр, `ё → е`, обрезка пробелов. Принимаются
русское и латинское написание: `минск/minsk`, `гомель/gomel/homel`. Страна — ISO-код (`BY`).

### 3.3 Фактор истории

Монолит присылает сводку по прошлым заявкам клиента (§8.1). Текущая заявка в сводку не входит.

```
нет подписанных займов и отказов за 12 месяцев  → 0.5 (нейтрально)
иначе: 0.5
       + min(0.1 × погашено_вовремя, 0.4)
       − 0.25 × погашено_с_просрочкой
       − 0.1 × отказов_за_12_месяцев
       и ограничить диапазоном [0, 1]
```

### 3.4 Классы, скорбалл и PD

Калибровка (тоже часть правил):

- при score = 0.5 (200 баллов, проходной порог задания) PD = 10 % — для микрозаймов реалистично;
- каждые +0.1 score (+40 баллов) вдвое уменьшают шансы невозврата (PDO, points to double odds).

Отсюда `b = ln 2 / 0.1 = 6.9315`, `a = ln(0.9 / 0.1) − 0.5 × b = −1.2685`.

| Класс | > Скорбалл | ≤ Скорбалл | PD мин | PD макс | Решение |
|---|---|---|---|---|---|
| A1 | 375 | 400 | 0,35% | 0,53% | RECOMMEND |
| A2 | 350 | 375 | 0,53% | 0,82% | RECOMMEND |
| A3 | 325 | 350 | 0,82% | 1,26% | RECOMMEND |
| B1 | 300 | 325 | 1,26% | 1,93% | RECOMMEND |
| B2 | 275 | 300 | 1,93% | 2,94% | RECOMMEND |
| B3 | 250 | 275 | 2,94% | 4,46% | RECOMMEND |
| C1 | 225 | 250 | 4,46% | 6,72% | RECOMMEND |
| C2 | 200 | 225 | 6,72% | 10,00% | RECOMMEND (проходной порог: score > 0.5) |
| C3 | 175 | 200 | 10,00% | 14,63% | REVIEW |
| D1 | 150 | 175 | 14,63% | 20,90% | REVIEW |
| D2 | 125 | 150 | 20,90% | 28,95% | REVIEW |
| D3 | 100 | 125 | 28,95% | 38,60% | AUTO_REJECT |
| E1 | 75 | 100 | 38,60% | 49,22% | AUTO_REJECT |
| E2 | 50 | 75 | 49,22% | 59,92% | AUTO_REJECT |
| E3 | — | 50 | 59,92% | 78,05% | AUTO_REJECT |
| F | — | — | — | — | AUTO_REJECT: возраст вне 18–90, чёрный список, текущая просрочка |

Пороги решений заданы в баллах на границах классов. Чтобы получить строгое «< 0.5 — отказ» из задания,
достаточно новой версии правил с `autoRejectMaxPoints = 200`: серая зона исчезнет без правки кода.

### 3.5 Примеры

| Заёмщик | история | цель | возраст | город | пол | score | баллы | класс | PD | решение |
|---|---|---|---|---|---|---|---|---|---|---|
| Ж, 45, Минск, 3 погашенных, «Лечение» | 0.8 | 0.8 | 0.5 | 0.9 | 1.0 | 0.785 | 314 | B1 | 1,5% | RECOMMEND |
| М, 30, Гомель, новый, «Техника» | 0.5 | 0.6 | 0.3 | 0.2 | 0.6 | 0.45 | 180 | C3 | 13,6% | REVIEW |

### 3.6 Что видит клиент

Только общую причину, без расшифровки факторов: «Заявка не прошла автоматическую проверку». Уведомление и
письмо — та же цепочка, что при ручном отказе (`loan.application.rejected`).

## 5. Просрочка

### 5.1 Переходы

```
SUBMITTED → APPROVED → ACTIVE ──(due_date прошла)──→ OVERDUE
                         │                              │
                         └──→ REPAID ←──────────────────┘
```

- При подписи договора: `due_date = дата подписи (Europe/Minsk) + term_days`.
- `LoanOverdueJob` (cron `app.loan.overdue-cron`, по умолчанию 00:10 по Минску; повторный запуск безопасен):
  `ACTIVE` с `due_date < сегодня` под `FOR UPDATE SKIP LOCKED` → `OVERDUE`, журнал, события
  `loan.application.overdue` (уведомление) и `loan.history.changed` (Mongo).
- Напоминания на 3 и 7 день просрочки (`app.loan.overdue-reminder-days`): событие для уведомления и строка
  журнала `OVERDUE_REMINDER_SENT {day}`; по ней повторный запуск задачи не шлёт напоминание дважды.
  День 1 — само уведомление о переходе в `OVERDUE`.
- «Погашен» доступен из `ACTIVE` и `OVERDUE`. Админ указывает **фактическую дату оплаты** `paidAt`
  (по умолчанию — сегодня; не в будущем и не раньше подачи заявки).
  Дни просрочки = `max(0, paid_at − due_date)`: заём, отмеченный из `OVERDUE`, но оплаченный до срока,
  записывается как погашенный вовремя.

### 5.2 Гонка «админ гасит — задача переводит в просрочку»

Задача берёт строку под `FOR UPDATE SKIP LOCKED`, админ передаёт `version`. Если первым успел админ —
задача пропустит заявку (уже не `ACTIVE`). Если первой успела задача — админ получит
`409 CONCURRENT_MODIFICATION`, обновит карточку и нажмёт «Погашен» снова (переход `OVERDUE → REPAID` разрешён).

### 5.3 Где учитывается OVERDUE

| Место | Что |
|---|---|
| Одна незакрытая заявка | `OVERDUE` считается незакрытой |
| KYC retention | `OVERDUE` — живая заявка, фото не удаляется |
| Mongo `credit_history` | `dueDate`, `paidAt`, `overdueDays`; в сводке — `overdueLoans`, `maxOverdueDays` |
| Бюро | VIEW и чтение Mongo включают `OVERDUE` |
| Скоринг | текущий `OVERDUE` → класс F; прошлые просрочки снижают фактор истории |
| Клиент | уведомление и письмо в день 1, 3, 7 |
| Админ | фильтр «OVERDUE» в существующем списке; с 30-го дня — подсказка «кандидат в ЧС» (фронтенд) |

Журнал контактов с должником и обещанные платежи — будущий сервис взыскания, в этот объём не входят.
Пролонгации нет.

## 6. Скоринг в монолите

### 6.1 Подача

`LoanApplicationService.submit` в одной транзакции: заявка `SUBMITTED` + `scoring_status = PENDING` +
новый `scoring_request_id` + событие `loan.scoring.requested` в outbox (§8.1).

### 6.2 Приём результата

Очередь `loan.scoring-result.q` (routing key `loan.scoring.completed`) → `ScoringResultService.apply`:

1. Заявки нет — warn и выход.
2. `requestId` не совпадает с `scoring_request_id` заявки — устаревший ответ (был повторный запрос), игнор.
3. Результат по этому `requestId` уже записан — повторная доставка, игнор.
4. Записать итог в заявку (статус, score, баллы, класс, PD, решение, версию правил).
5. `AUTO_REJECT` и заявка всё ещё `SUBMITTED` → `REJECTED` системой (`decided_by = null`), причина
   из §3.6, журнал, событие `loan.application.rejected` → уведомление и письмо.
   Если заявку уже отменили или отклонили — результат только записывается.

Сохранение с `@Version`: гонка с действием админа даёт исключение → повтор доставки → шаг 5 видит новый статус.

### 6.3 Запрет решения без скоринга

- `approve` → `409 SCORING_REQUIRED`, если `scoring_status` не `COMPLETED` и не `NOT_CALCULATED`.
  `NOT_CALCULATED` — сервис посчитал и явно сказал «ручное рассмотрение».
- `reject` без скоринга разрешён: отказ по явным признакам мошенничества не должен ждать сервис.
- `POST /api/admin/loan-applications/{id}/scoring` — запросить скоринг заново (новый `requestId`,
  `PENDING`). Только для `SUBMITTED`. Нужен, если результат не пришёл (сообщение ушло в DLQ), и для старых
  заявок, поданных до появления скоринга.

### 6.4 Что видит админ

В строке списка и карточке: `scoringStatus`, класс, скорбалл, PD, решение. Расшифровку по факторам
админка берёт из credit-policy напрямую: `GET /credit-policy/api/admin/scorings/{applicationId}`.

## Часть B. Микросервис `credit-policy/`

## 7. Устройство

- Spring Boot 4.0.9, Java 25, порт 8092, context path `/credit-policy`; снаружи — только через nginx `/credit-policy/`.
- Своя БД `nosurprise_scoring` (Flyway). **В базу монолита и Mongo не ходит**: все данные приходят в событии.
- RabbitMQ: читает `loan.scoring.requested`, публикует `loan.scoring.completed`.
- Аутентификация админского API — JWT монолита (HS256, общий `JWT_SECRET`, claim `roles`), нужна роль `ADMIN`.
  Монолит запросы админки к credit-policy не проксирует.

### 7.1 Таблицы (`V1__credit_policy.sql`)

| Таблица | Колонки | Назначение |
|---|---|---|
| `rule_sets` | `version` PK, `rules jsonb`, `active`, `comment`, `created_by`, `created_at` | Версии правил; активна ровно одна (частичный уникальный индекс) |
| `blacklist_entries` | `id`, `phone`, `last_name_norm`, `first_name_norm`, `middle_name_norm`, `birth_date`, `reason`, `added_by`, `created_at`, `expires_at`, `removed_at`, `removed_by` | Чёрный список |
| `scoring_results` | `id`, `request_id` UNIQUE, `application_id`, `user_id`, `status`, `score`, `points`, `rating_class`, `pd`, `decision`, `reasons jsonb`, `breakdown jsonb`, `input jsonb`, `rules_version`, `created_at` | Журнал расчётов: вход, расшифровка, версия правил |

### 7.2 Обработка запроса

```
сообщение loan.scoring.requested
 ├─ результат с этим requestId уже есть → опубликовать его ещё раз (идемпотентность)
 └─ иначе: активные правила + балл цели из события + чёрный список → ScoringEngine (чистая функция)
           → сохранить scoring_results → опубликовать loan.scoring.completed (с подтверждением брокера)
```

Сбой публикации после сохранения → исключение → повтор доставки → шаг «уже есть» опубликует сохранённый
результат. Отдельный outbox не нужен. 3 попытки, затем DLQ; дальше — повтор по кнопке админа (§6.3).

### 7.3 Цель займа — это тип займа

Отдельного справочника целей нет: тип займа в монолите и есть цель («На iPhone» — техника, «Последний шанс» —
до зарплаты). Две таблицы с одним смыслом пришлось бы вести в двух сервисах.

- Балл цели 0–1 хранится у типа займа (`loan_types.purpose_score`, по умолчанию 0.50). Задаёт админ в CRM
  вместе с остальными параметрами типа; `null` при изменении — «не менять».
- Монолит кладёт название типа и балл цели в событие `loan.scoring.requested`. credit-policy в БД монолита
  не ходит и копию типов займа не держит.
- Балл попадает в `scoring_results.input` вместе с остальным входом: расчёт воспроизводим, даже если админ
  потом изменит балл у типа.
- Компромисс: один из параметров модели живёт не в credit-policy, а в монолите, и в `rule_sets` не
  версионируется. При выносе типов займа в отдельный сервис балл уедет вместе с ними.

### 7.4 Чёрный список

| | Блокировка (есть в монолите) | Чёрный список (credit-policy) |
|---|---|---|
| Запрещает | вход в аккаунт | только новые займы |
| По чему | `user_id` | телефон **или** фамилия + имя (+ отчество, если указано) + дата рождения |
| Должник может войти и погасить | нет | да |
| Кто ставит | админ | админ, с причиной и необязательным сроком; снять — тоже админ (запись не удаляется) |

Автоматически в ЧС никто не попадает.

## Часть C. Бюро

## 10. Просрочка в отчёте бюро

VIEW `bureau_applicant_lookup` включает `OVERDUE` (миграция монолита V17). Бюро читает из Mongo
`ACTIVE`, `OVERDUE`, `REPAID`; в займе отчёта — `dueDate`, `paidAt`, `overdueDays`.
Класс и PD «по человеку» для банков — следующий шаг (§13).

## 11. Инфраструктура

- `docker-compose.yml`: сервис `credit-policy`; `db-init` создаёт `nosurprise_scoring`.
- nginx: `location /credit-policy/` → `credit-policy:8092` (через resolver, как бюро).
- Переменные: `JWT_SECRET` (общий), `RABBITMQ_*`, `POLICY_DB_*`.

## 12. Тесты

- Unit: `ScoringEngine` (стоп-факторы, границы возраста 17/18/39/40/60/61/90/91, города, история, классы,
  PD на якорных точках, пороги решений), валидация правил, нормализация.
- Монолит (unit): переходы `OVERDUE`, дни просрочки, запрет `approve` без скоринга, приём результата.
- Integration (Testcontainers, `@Tag("integration")`): credit-policy — расчёт по сообщению и идемпотентность;
  монолит — существующие сценарии с имитацией ответа скоринга.

## 13. Не входит / потом

- Класс и PD в отчёте бюро «по человеку» (без заявки).
- Сервис взыскания: журнал контактов, обещанные платежи.
- Статистическая калибровка PD по накопленным просрочкам.

## 14. Зафиксированные решения

1. Модель экспертная: средневзвешенное → скорбалл 0–400 → класс → PD (логистическая калибровка).
2. Веса: история 30 %, цель 20 %, возраст 20 %, город 15 %, пол 15 %.
3. Возраст 18–90, лучший диапазон 40–60 (включительно), 61–90 ниже.
4. Прочие города Беларуси — 0.15.
5. Цель займа — тип займа: балл цели хранится у типа в монолите и приходит в событии (справочник целей убран).
6. Три зоны решения на границах классов; проходной порог задания (score > 0.5) — граница RECOMMEND.
7. Клиенту при автоотказе — только общая причина, уведомление и письмо.
8. Админ не одобряет без результата скоринга; отклонять без скоринга можно.
9. Профиль без новых полей → подать заявку нельзя (форма профиля требует их обязательно).
10. Чёрный список ведёт только админ; это не блокировка аккаунта.
11. Расчёт асинхронный через RabbitMQ; credit-policy не ходит в БД монолита.
12. Просрочка: статус `OVERDUE`, фактическая дата оплаты при погашении, напоминания 1/3/7 день, без пролонгации.
13. Минимум изменений в монолите: риск живёт в credit-policy.
