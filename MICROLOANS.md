# MICROLOANS.md — микрозаймы: требования и правила реализации

Статус: **на ревью у автора.** Открытых вопросов нет, все решения зафиксированы (сводка в §10).
Документ дополняет `INSTRUCTION.md`: общие правила (стек, слои, деньги, ошибки, RabbitMQ) действуют и здесь.
Где этот документ расходится с `INSTRUCTION.md` (outbox вместо `AFTER_COMMIT`), для модулей микрозаймов главный он.
Если решение меняется, обнови этот файл в том же PR.

## 1. Цель и границы

Клиент подбирает микрозайм под свою цель, заполняет данные, проходит KYC и подаёт заявку.
Админ рассматривает её в CRM и одобряет или отклоняет. Одобренный договор клиент скачивает
и подписывает кодом из SMS. После подписи заём получает статус `ACTIVE`, а когда клиент рассчитался,
админ вручную отмечает его погашенным (`REPAID`).

**Входит в первую версию:**
- типы микрозаймов, которыми управляет админ;
- калькулятор;
- профиль клиента: ФИО, телефон, паспорт;
- KYC: фото паспорта;
- заявка, её рассмотрение, уведомления;
- история микрозаймов: клиенту — своя, админу — со сводкой и кредитной историей для решения;
- личный кабинет клиента (§3.13);
- договор в PDF, подпись кодом из SMS;
- ручная отметка админа «Погашен»;
- панель пользователей;
- transactional outbox для событий;
- кредитная история в MongoDB: копия всех состояний всех займов, согласованная с Postgres (§3.14, §4.9).

**Не входит:**
- выдача денег, приём платежей и их учёт, автоматическая просрочка;
- неустойки (есть только фиксированный модификатор типа, §3.1).
- кредитное бюро, автоматический скоринг;

Код пишем так, чтобы это добавлялось без переделки (см. §7).

## 2. Термины

| Термин | Значение |
|---|---|
| Тип займа (`LoanType`) | продукт под цель: «На ремонт», «До зарплаты». Задаёт лимиты и ставку |
| Заявка (`LoanApplication`) | запрос клиента на заём конкретного типа, суммы и срока. Проходит путь до `ACTIVE` |
| Снимок (snapshot) | копия условий типа и данных клиента в момент подачи. После подачи не меняется |
| Пользователь (`users`) | учётная запись для входа и безопасности |
| Клиент (`customer_profile`) | бизнес-данные человека: ФИО, телефон, месячная зарплата |
| KYC-документ | фото паспорта клиента |
| Рабочий день | понедельник–пятница (§3.8) |
| ПДН | показатель долговой нагрузки: доля зарплаты, которая уйдёт на погашение займа. Считается на лету, не хранится (§3.7) |
| История микрозаймов | все заявки пользователя из Postgres (§3.12) |
| Модификатор | фиксированная надбавка типа займа в BYN, прибавляется к сумме к возврату (§3.1) |
| Кредитная история | копия всех займов клиента со всеми состояниями и проколами в MongoDB (§3.14) |
| Прокол | событие, которое говорит о ненадёжности клиента: не подписал вовремя, ошибся с кодом подписи и т. п. (§3.14) |
| Outbox | таблица событий, которые записаны в одной транзакции с данными и ждут отправки в RabbitMQ (§4.8) |

## 3. Бизнес-требования

### 3.1 Типы займов
- Создаёт и меняет только ADMIN.
- Поля: название, описание цели, сумма от/до, срок от/до в днях, дневная ставка в процентах,
  **модификатор** (фиксированная надбавка в BYN, задаёт админ), активен ли.
- **Валюта — белорусские рубли (BYN), одна на всю систему.** Колонки валюты нет. На фронте суммы выводятся с `BYN`.
- Срок любого типа лежит в пределах **7–30 дней**: `7 ≤ min_term_days ≤ max_term_days ≤ 30`.
- `min_amount > 0`, `min_amount ≤ max_amount`, `daily_rate ≥ 0`, `modifier ≥ 0`.
- Тип **не удаляется**, а выключается (`active = false`): на него ссылаются старые заявки.
  Выключенный тип не показывается клиенту и не принимает новые заявки.
- Изменение типа **не влияет** на уже поданные заявки: у них свой снимок условий (§3.6).
- На старте два типа, они задаются seed-миграцией. Суммы, сроки, ставки и модификатор «До зарплаты» вымышленные,
  админ меняет их в CRM:

| Название | Сумма, BYN | Срок, дней | Ставка в день | Модификатор, BYN |
|---|---|---|---|---|
| На iPhone | 1000–5000 | 14–30 | 0.500 % | 150.00 |
| До зарплаты | 100–1000 | 7–14 | 1.000 % | 20.00 |

### 3.2 Калькулятор
Простые проценты за каждый день плюс модификатор типа, одним платежом в конце срока. Неустоек нет.
```
interest = round(amount × daily_rate / 100 × term_days)
total    = amount + interest + modifier
```
- Проценты считаются только от суммы займа, на модификатор не начисляются.
- Округление `HALF_UP` до копеек, через `Money`.
- Калькулятор публичный и ничего не сохраняет.
- Эталон для тестов: 1000.00 BYN, 1 % в день, 10 дней, модификатор 150.00 → проценты 100.00, к возврату 1250.00 BYN.
- Ответ калькулятора: `interest`, `modifier`, `total`.
- Сумма или срок вне лимитов типа → `400 LOAN_PARAMS_OUT_OF_RANGE`.

### 3.3 Флоу клиента
1. **Расчёт.** Клиент выбирает тип, сумму и срок и видит проценты, модификатор и сумму к возврату.
2. **Данные.** Форма: фамилия, имя, отчество (может отсутствовать), телефон, месячная зарплата в BYN.
   Зарплата хранится в профиле и копируется в снимок заявки (§3.6).
   Поля, которые уже есть в профиле, подставляются сами.
3. **Подтверждение телефона.** Прямо в форме на телефон приходит код, клиент его вводит.
   Подать заявку можно и без подтверждения, но **без подтверждённого телефона нельзя подписать договор**
   и перевести заём в `ACTIVE` (§3.10). Смена номера сбрасывает подтверждение.
4. **KYC.** Клиент загружает фото паспорта. Если оно уже загружено и ещё не удалено (§3.11),
   можно оставить старое или заменить.
5. **Подача.** Профиль обновляется (только изменённые поля), создаётся заявка со снимками (§3.6).
   Всё это одна транзакция вместе с событием (§4.8). Клиент видит «Заявка на рассмотрении».
6. **Ожидание.** Статус виден в личном кабинете. До решения заявку можно отозвать.
7. **Решение.** При одобрении письмо «Ваша заявка на микрозайм одобрена» (без сумм и ФИО) уходит, когда договор
   уже сгенерирован; ссылка ведёт в «Мои заявки» с раскрытой подписью. При отказе — письмо «По вашей заявке принято
   решение». В личном кабинете виден результат. **При отказе показывается причина**, которую указал админ.
8. **Документы.** При одобрении в уведомлении на сайте есть PDF договора для скачивания и блок подписи
   (если телефон не подтверждён — сначала его подтверждение кодом).
9. **Подпись.** Клиент запрашивает код на подтверждённый телефон, вводит его и получает подтверждение.
   Заявка переходит в `ACTIVE`, приходит письмо «Договор подписан».
10. **Погашение.** Когда клиент рассчитался, админ отмечает заём погашенным (`REPAID`). Приходит письмо «Заём закрыт»,
   и клиент может подать новую заявку.

### 3.4 Флоу админа: заявки
- Список заявок с фильтром по статусу (по умолчанию `SUBMITTED`), сортировка по дате подачи, пагинация.
- В строке: дата, ФИО, тип, сумма, срок, зарплата, ПДН, статус.
- Карточка заявки:
  - снимок данных и условий;
  - фото паспорта (по кнопке, просмотр логируется, §5);
  - зарплата и ПДН по этой заявке (§3.7);
  - сводка и история микрозаймов клиента (§3.12);
  - кредитная история с проколами (§3.14) — чтобы админ понял, надёжный ли клиент.
- Действия по заявке в `SUBMITTED`: **одобрить** (комментарий необязателен) или **отклонить** (причина обязательна, её увидит клиент).
- Действие по займу в `ACTIVE`: **«Погашен»** → `REPAID`.
- Админ не может решать по собственной заявке.
- Кто и когда принял решение, сохраняется.

### 3.5 Панель пользователей
- Список пользователей с поиском по email и ФИО, пагинация.
- Карточка: учётная запись (email, роли, способ входа, подтверждена ли почта), профиль, сводка и история микрозаймов (§3.12).
- **Блокировка:** заблокированный не может войти, обновить токен и подать или подписать заявку.
  При блокировке все его refresh-токены удаляются (`refresh:{userId}:*`).
- Админ не может заблокировать себя.

### 3.6 Снимки
При подаче в заявку копируются:
- **условия:** `daily_rate`, `modifier`, рассчитанные `interest` и `total`;
- **данные заявителя:** ФИО, телефон, месячная зарплата, ссылка на конкретный KYC-документ.

Зачем:
- админ видит то, что человек подал, а не то, что он поменял потом;
- договор строится по условиям, на которые клиент согласился;
- список заявок строится без join на профиль и пользователей.

### 3.7 Платёжеспособность: ПДН
Проверка платёжеспособности в первой версии — **показатель долговой нагрузки (ПДН)**.
Он **не хранится**, а считается на лету при показе заявки админу и клиенту, из снимка заявки:
```
ПДН = total / monthly_income × 100 %
```
- `monthly_income` — зарплата из снимка заявки, то есть на момент подачи.
- Округление до 0.01 %, `HALF_UP`.
- Зарплата строго больше нуля, иначе `400` (валидация профиля и формы).
- Если ПДН выше `app.loan.debt-load-warning-percent: 50`, админ видит предупреждение. Автоматического отказа нет.
- Расчёт — чистая функция `DebtLoad.percent(total, monthlyIncome)` (§7.5). Решение принимает админ.

Отдельной таблицы ПДН нет: всё нужное уже есть в снимке заявки.

### 3.8 Статусы заявки

| Из | В | Кто | Условие |
|---|---|---|---|
| — | `SUBMITTED` | клиент | профиль заполнен, есть неудалённое фото паспорта, нет другой активной заявки или займа |
| `SUBMITTED` | `CANCELLED` | клиент | — |
| `SUBMITTED` | `APPROVED` | админ | не своя заявка |
| `SUBMITTED` | `REJECTED` | админ | причина указана |
| `APPROVED` | `ACTIVE` | клиент | телефон подтверждён, код верный, предложение не истекло |
| `APPROVED` | `EXPIRED` | система | не подписан за 5 рабочих дней |
| `ACTIVE` | `REPAID` | админ | клиент рассчитался |
| `ACTIVE` | `OVERDUE` | система | прошла дата возврата (CREDIT_POLICY.md §5) |
| `OVERDUE` | `REPAID` | админ | клиент рассчитался с опозданием; админ указывает фактическую дату оплаты |

- Остальные переходы запрещены → `409 INVALID_STATUS_TRANSITION`.
- Конечные статусы: `CANCELLED`, `REJECTED`, `EXPIRED`, `REPAID`.
- Реализация переходов инкапсулирована в паттерне State: интерфейс `dev.nosurprise.loan.application.state.LoanState` и
  по одному классу на статус (`SubmittedState`, `ApprovedState`, `ActiveState`, `RejectedState`, `CancelledState`,
  `ExpiredState`, `RepaidState`) в пакете `dev.nosurprise.loan.application.state`. Каждое состояние знает
  допустимые переходы (`allowedTransitions`), валидирует переход (`validateTransition`) и выполняет действия
  при входе/выходе (`onEnter` / `onExit`). `LoanStatus` остаётся только идентификатором для JPA, CHECK constraint
  и OUTBOX-событий.
- **У пользователя не больше одного активного микрозайма.** Активными считаются статусы `SUBMITTED`, `APPROVED` и `ACTIVE`.
  Пока такой есть, новую заявку подать нельзя → `409 ACTIVE_APPLICATION_EXISTS`.
- После `REPAID` активного займа нет, клиент может подать новую заявку.
- `OVERDUE` тоже считается незакрытым: должник новую заявку не подаст. Одобрить заявку админ может только после
  результата скоринга (CREDIT_POLICY.md §6.3).

**Срок предложения.**
- `offer_expires_at = decided_at + 5 рабочих дней`, время суток сохраняется.
- Рабочие дни — пн–пт в часовом поясе `app.loan.business-zone: Europe/Minsk`. Праздники не учитываются.
- Считается каждый следующий пн–пт после дня решения.
- Примеры: пятница 15:00 → следующая пятница 15:00; суббота 15:00 → следующая пятница 15:00.
- Количество дней в настройке `app.loan.offer-ttl-business-days: 5`.

### 3.9 Уведомления

| Событие | Запись в `notifications` | Письмо |
|---|---|---|
| заявка подана | — | «Заявка принята» |
| договор готов (после одобрения) | да, со ссылками на PDF и подпись | «Принято решение, зайдите в ЛК» |
| отклонена | да, с причиной | «Принято решение, зайдите в ЛК» |
| подписана (`ACTIVE`) | да | «Договор подписан» |
| истекла | да | «Срок подписания истёк» |
| погашена (`REPAID`) | да | «Заём закрыт» |

- Уведомление об одобрении создаётся, **когда PDF уже готов**, а не в момент решения.
  Иначе клиент откроет ссылку на договор, которого ещё нет (§4.5).
- В письмах нет сумм, ФИО и причин отказа, только ссылка в личный кабинет.

### 3.10 Документы и подпись
- Договор в PDF генерируется **при одобрении** из снимка заявки, асинхронно (как PDF сценариев).
  Хранится в **GridFS**.
- Хранится SHA-256 договора. Подписывается именно этот документ: подпись ссылается на хэш.
- Код отправляется только на **подтверждённый** телефон профиля. Если телефон не подтверждён → `409 PHONE_NOT_VERIFIED`.
- Код подписи:
  - 6 цифр, живёт 5 минут;
  - не больше 3 попыток ввода;
  - повторная отправка не чаще раза в 60 секунд.
- При подписи сохраняются: id заявки, хэш договора, телефон, время, IP, user-agent.
  Это доказательство того, кто, когда и что подписал.
- Подписи кодом из SMS для нашей юрисдикции достаточно.

### 3.11 Фото паспорта
- Только фото главного разворота паспорта, одним файлом. Ни селфи, ни прописки.
- JPEG или PNG, до 5 МБ.
- **Срок хранения.** Содержимое фото удаляется через **7 дней** после того, как заявка, которая на него ссылается,
  перешла в `REJECTED`, `CANCELLED` или `EXPIRED`. Условие удаления: на фото не ссылается ни одна заявка
  в `SUBMITTED`, `APPROVED`, `ACTIVE` или `REPAID`.
- Удаляется только содержимое (`content = null`, `deleted_at`). Строка с метаданными и хэшем остаётся для аудита.
- Удаляет ежедневная задача.
- Фото по подписанному займу (`ACTIVE`, `REPAID`) не удаляется: это личность, на которую оформлен договор.

### 3.12 История микрозаймов
**Клиент** видит свою историю в личном кабинете. Источник — Postgres: клиент сразу видит свои действия, без задержки.
- дата подачи, тип, сумма, срок, модификатор, сумма к возврату;
- статус, причина отказа (если есть);
- зарплата на момент подачи и ПДН.

**Админ** видит на карточке заявки и на карточке пользователя **кредитную историю из MongoDB** (§3.14):
- **сводку:**
  - сколько всего займов и сколько в каждом статусе;
  - есть ли сейчас активный заём;
  - зарплата и ПДН по последней заявке, минимальный и максимальный ПДН за всё время;
  - число проколов по типам;
  - дата первой заявки;
- **все займы клиента** со всеми состояниями, хронологией, решениями админов и проколами.

Сводка — подсказка для решения. Правил автоотказа по ней нет.
Системные проверки (один активный займ, допустимые переходы) делаются только по Postgres.

### 3.13 Личный кабинет
Личный кабинет — единое место для всех действий клиента после входа. Разделы:

| Раздел | Что внутри |
|---|---|
| Профиль | ФИО, телефон и его подтверждение, статус фото паспорта (загружено / удалено по сроку), загрузка нового фото. Email только для чтения (меняется через учётную запись) |
| Мои займы | история микрозаймов (§3.12); активная заявка или заём сверху |
| Карточка займа | условия из снимка (с модификатором), статус, причина отказа, PDF договора, кнопка подписи (только в `APPROVED`, пока не истёк срок), срок до истечения предложения |
| Уведомления | существующий раздел `notifications`; уведомления по займам ведут в карточку займа |

- Из письма и уведомления клиент попадает в карточку займа, а не на отдельную страницу подписи.
- Неавторизованный пользователь из ссылки в письме попадает на вход, после входа — обратно в карточку.
- Подать новую заявку можно из раздела «Мои займы», если нет активной (§3.8).

### 3.14 Кредитная история (MongoDB)
Postgres хранит все операции и меняет статусы. **MongoDB дублирует все состояния всех займов**: на каждое изменение
займа в Postgres обновляется его документ в коллекции `credit_history`. Так админ видит полную картину по клиенту,
в том числе когда займов станет больше одного.

- Один документ на один заём (заявку), `_id = applicationId`.
- В Mongo попадают **все статусы**: `SUBMITTED`, `APPROVED`, `ACTIVE`, `REJECTED`, `CANCELLED`, `EXPIRED`, `REPAID`.
- Postgres — источник правды, Mongo — копия. Как они остаются согласованными — §4.9.

Что в документе:
- условия займа из снимка: тип, сумма, срок, ставка, модификатор, проценты, сумма к возврату;
- зарплата на момент подачи и ПДН;
- текущий статус и полная хронология статусов: кто и когда менял;
- решение админа: кто, когда, комментарий или причина;
- **проколы клиента** по этому займу, каждый с типом и временем.

Проколы (тип хранится строкой, список расширяется без смены схемы):

| Тип | Когда |
|---|---|
| `OFFER_NOT_SIGNED` | предложение истекло без подписи |
| `SIGN_CODE_FAILED` | введён неверный код подписи |
| `SIGN_CODE_BURNED` | код сгорел после 3 неверных попыток |
| `SIGN_BLOCKED_PHONE_NOT_VERIFIED` | пытался подписать без подтверждённого телефона |

Все события по займу (смены статусов и проколы) пишутся в Postgres в журнал `loan_events` (§4.3)
в той же транзакции, что и действие. Из журнала и собирается документ в Mongo.

### 4.7 Панель заявок: как не утонуть в запросах
- **Список** — один запрос к `loan_applications` с join на `loan_types` (название). Зарплата и модификатор из снимка, ПДН считается в маппере.
  Данные заявителя берутся из снимка, join на профиль и пользователей не нужен. Проекция сразу в DTO, пагинация.
- **Карточка** — один эндпоинт. Бэк сам делает 2–3 запроса (заявка из Postgres; кредитная история из Mongo одним `find` по индексу `userId`, сводка считается по этим же документам в памяти — у клиента десятки займов) и отдаёт один ответ.
- **Фото паспорта** не входит ни в список, ни в карточку. Отдельный запрос, только по кнопке.
- В JPA никаких ленивых связей в цикле (N+1): проекции или `@EntityGraph`.
- Кэши и отдельные read-модели сейчас не нужны.

### 4.8 Transactional outbox

**Проблема.** Подача заявки — это в одной транзакции частичное обновление профиля (включая зарплату) и создание заявки.
После неё нужно отправить событие, по которому уйдёт письмо.

Сейчас в проекте событие уходит в RabbitMQ после коммита (`AFTER_COMMIT`). Если приложение упадёт между коммитом
и отправкой или RabbitMQ недоступен, заявка в базе есть, а события нет. Письма нет, PDF не создан, клиент ждёт вечно.
Отправлять до коммита ещё хуже: при откате письмо про несуществующую заявку уже ушло.

**Решение.** Событие пишется в таблицу `outbox_events` **в той же транзакции**, что и бизнес-данные.
Отдельный relay отправляет его в RabbitMQ. Либо закоммитилось всё вместе, либо ничего.

```
Транзакция подачи (PostgreSQL):
  UPDATE customer_profile ...     только изменённые поля, с проверкой version
  INSERT loan_applications ...    заявка со снимками
  INSERT loan_events ...          STATUS_CHANGED → SUBMITTED
  INSERT outbox_events ...        loan.application.submitted, loan.history.changed
COMMIT

Relay (каждую секунду, app.outbox.poll-interval):
  BEGIN
  SELECT ... FROM outbox_events WHERE published_at IS NULL
    ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED
  для каждой строки: publish в domain.events, ждём подтверждения брокера
  UPDATE outbox_events SET published_at = now() WHERE id IN (...)
  COMMIT
```

**Таблицы:**

| Таблица | Поля |
|---|---|
| `outbox_events` | id bigserial, event_id uuid unique, aggregate_type, aggregate_id, event_type (routing key), payload jsonb, created_at, published_at (null), attempts int, last_error text (null) |
| `processed_events` | consumer, event_id, processed_at; PK (consumer, event_id) |

Индекс: `outbox_events (id) where published_at is null`.

**Правила:**
- Запись в outbox — только внутри существующей транзакции: `OutboxPublisher.publish(event)` помечен
  `@Transactional(propagation = MANDATORY)`. Вызов без транзакции — ошибка, а не тихая потеря.
- Бизнес-код не вызывает `RabbitTemplate` напрямую, только `OutboxPublisher`.
- Relay:
  - `SKIP LOCKED`, чтобы несколько инстансов не взяли одну строку;
  - publisher confirms (`spring.rabbitmq.publisher-confirm-type: correlated`), строка помечается отправленной
    только после подтверждения брокера;
  - при ошибке `attempts + 1`, `last_error`, повтор на следующем цикле;
  - после `app.outbox.max-attempts` (10) — `ERROR` в лог, строка остаётся для разбора.
- **Гарантия at-least-once.** Сообщение может прийти дважды: отправили, упали до `UPDATE`. Поэтому каждый consumer:
  - вставляет `(consumer, event_id)` в `processed_events` в той же транзакции, что и свою работу;
  - конфликт по PK означает, что событие уже обработано: пропускаем.
- **Порядок не гарантируется** при ретраях. Consumer не полагается на порядок, а проверяет текущий статус заявки.
- Consumer, который сам порождает событие (PDF готов → уведомление), публикует его тоже через outbox, в своей транзакции.
- Очистка: отправленные строки `outbox_events` старше 7 дней и `processed_events` старше 30 дней удаляются ежедневной задачей.

**Где транзакция Postgres не покрывает всё:**
- **Договор в GridFS.** MongoDB не участвует в транзакции Postgres. Порядок:
  1. сгенерировать PDF;
  2. сохранить в GridFS под именем `contract-{applicationId}.pdf`;
  3. в транзакции Postgres записать `loan_documents`, outbox `loan.contract.ready` и `processed_events`;
  4. после коммита удалить файлы с тем же именем, кроме того, на который ссылается `loan_documents`.

  Если упадём между шагами 2 и 3, при повторной доставке появится новый файл, а старый сирота удалится на шаге 4.
  Удалять до сохранения нельзя: параллельная доставка могла бы удалить файл, на который уже ссылается договор.
  Если вставка упала на уникальном `(application_id, type)` — договор уже сохранил другой consumer, свой файл удаляем.
- **Коды OTP в Redis.** Код проверяется до транзакции, ключ удаляется после коммита. Если удаление не удалось,
  повторно код не сработает: заявка уже не в `APPROVED`.
- **Загрузка паспорта** — отдельный запрос со своей транзакцией. При подаче заявки только ссылка на уже сохранённый документ.

**Своя таблица, а не Spring Modulith.** Event Publication Registry из Spring Modulith делает похожее из коробки,
но мы пишем свою простую таблицу: около 150 строк кода, полностью прозрачно, легко объяснить и тестировать.

**Существующие модули** (`offer`, `scenario`, `notification`, `pdf`) остаются на `AFTER_COMMIT`.
Их перевод на outbox не входит в эту фичу и делается отдельной задачей, после неё обновить §8 `INSTRUCTION.md`.

### 4.9 Согласованность Postgres и MongoDB

**Источник правды — Postgres.** Каждое изменение займа сначала коммитится в Postgres. Mongo получает копию через outbox.
В коллекцию `credit_history` пишет **только** consumer `loan.credit-history.q` и пересборка. Больше никто.

**Главный приём: документ не правится по кусочкам, а каждый раз собирается целиком из Postgres.**
Consumer не применяет «изменение» из события. Он читает текущее состояние заявки и весь её журнал `loan_events`
и заменяет документ полностью. Поэтому неважно, сколько раз и в каком порядке пришли события:
результат всегда равен текущему состоянию в Postgres.

**Версия документа — `lastEventId`**: максимальный `loan_events.id` заявки на момент чтения. `bigserial` только растёт,
поэтому более свежее состояние всегда имеет больший `lastEventId`.

**Документ `credit_history`:**
```
_id: applicationId            тот же id, что в Postgres
userId
schemaVersion: 1
lastEventId                   версия документа
status                        текущий статус
loan: {typeId, typeName, amount, termDays, dailyRate, modifier, interest, total}   Decimal128
monthlyIncome, debtLoadPercent                                                     Decimal128
submittedAt, decidedAt, decidedBy, decisionComment, closedAt
timeline: [{status, at, actorId}]
incidents: [{type, at, details}]
syncedAt
```
- Индексы: `(userId, submittedAt desc)` — история клиента; `(userId, status)` — сводка.
- Нет ФИО, телефона и паспорта: только `userId`. Персональные данные остаются в Postgres.
- Запись с `writeConcern: majority`.

**Путь записи:**
```
1. Любое действие с займом, одна транзакция Postgres:
     изменение заявки (статус и т. п.)
     INSERT loan_events ...                       смена статуса или прокол
     INSERT outbox_events (loan.history.changed)  + бизнес-событие, если есть
   COMMIT
2. Relay отправляет события в RabbitMQ (§4.8).
3. Consumer loan.credit-history.q на loan.history.changed {applicationId}:
     a. прочитать заявку и все её loan_events из Postgres → собрать документ, lastEventId = max(id);
     b. Mongo: replaceOne({_id: applicationId, lastEventId: {$lt: N}}, doc);
        если ничего не заменилось → insertOne(doc);
        если insertOne дал duplicate key → в Mongo уже версия не старее N, ничего не делаем;
     c. транзакция Postgres:
          UPDATE loan_applications SET credit_history_synced_event_id = N
            WHERE id = ? AND (credit_history_synced_event_id IS NULL OR credit_history_synced_event_id < N)
        COMMIT
```
`processed_events` этому consumer-у не нужен: шаги a–c идемпотентны сами по себе.

**Почему это согласованно при любом сбое:**

| Сбой | Что будет | Почему не страшно |
|---|---|---|
| Упали до коммита шага 1 | изменения нет нигде | ни Postgres, ни Mongo не изменились |
| Упали после коммита, до отправки | событие в outbox | relay отправит позже (§4.8) |
| Mongo недоступна на шаге b | ретраи, потом DLQ | `synced_event_id` отстаёт, сверка переотправит |
| Упали между b и c | Mongo свежая, отметка в Postgres старая | повтор соберёт тот же документ, `replaceOne` ничего не испортит, отметка догонит |
| Событие пришло дважды | — | тот же документ, та же версия |
| События пришли не по порядку | старое после нового | старое состояние имеет меньший `lastEventId`, условие `$lt` не даст им перезаписать новое |
| Два consumer-а одновременно | гонка записи | побеждает больший `lastEventId`, меньший отбрасывается условием |
| Кто-то записал в Mongo руками | расхождение | пересборка из Postgres перезаписывает документ |

**Сверка (страховка, если сообщение ушло в DLQ):**
- Задача раз в час `app.credit-history.reconcile-interval` ищет заявки, у которых
  `credit_history_synced_event_id` меньше последнего `loan_events.id` и последний event старше 15 минут.
- Для каждой — новое событие `loan.history.changed` через outbox.
- Раз в сутки — обратная проверка: количество заявок в Postgres против количества документов в Mongo.
  Расхождение → `ERROR` в лог с id заявок.

**Пересборка:** `POST /api/admin/credit-history/rebuild` (ADMIN) проходит по всем заявкам в Postgres и для каждой
делает шаги a–c. Коллекцию можно удалить целиком и собрать заново — данные не теряются, потому что источник правды в Postgres.

**Чего не делаем:**
- Не пишем в Postgres и Mongo из одного метода сервиса подряд (dual write).
- Не правим документ в Mongo частично (`$set`, `$push`): только полная замена из Postgres.
- Не делаем системных проверок (один активный займ, переходы статусов) по данным из Mongo.
- Копия отстаёт от Postgres на секунды. Клиенту его собственные займы показываем из Postgres (§3.12).

## 5. Безопасность и персональные данные

- **Проверка владельца на каждом клиентском эндпоинте** заявки, документа и истории.
  Чужая заявка → `404`, а не `403`, чтобы не раскрывать существование.
- **Фото паспорта:**
  - отдаётся только админу и только отдельным эндпоинтом;
  - каждый просмотр пишется в лог приложения строкой INFO: id админа, id документа, IP. Отдельной таблицы нет.
- **Персональные данные не попадают** в логи, письма, события RabbitMQ, outbox, `loan_events.details`, Mongo `credit_history` и URL.
  Телефон в логах маскируется (`+375 29 ***-**-67`).
- **Загрузка файлов:**
  - JPEG и PNG, до 5 МБ (`app.kyc.max-file-size: 5MB`);
  - тип проверяется по сигнатуре файла (magic bytes), а не по `Content-Type`;
  - имя файла от клиента не используется.
- **Заблокированный пользователь:** проверка `blocked` при входе, refresh и любом действии с заявкой.
  Access JWT живёт до 15 минут, это окно принимаем.
- Админ не решает по своей заявке и не блокирует себя.

## 6. Опасности и узкие места

| Опасность | Что будет | Что делаем |
|---|---|---|
| Админ поменял ставку типа | у поданных заявок меняются условия | снимок условий (§3.6) |
| Двойной клик «Подать» или параллельные запросы | два активных микрозайма | частичный уникальный индекс (§4.3), нарушение → `409 ACTIVE_APPLICATION_EXISTS` |
| Два админа решают одну заявку | второй перезапишет решение первого | `@Version`, клиент передаёт `version`, конфликт → `409 CONCURRENT_MODIFICATION` |
| Профиль меняется в двух вкладках | потеря правок | `@Version` на `customer_profile` |
| Приложение упало между коммитом и отправкой события | заявка есть, письма и PDF нет | outbox (§4.8) |
| Событие пришло дважды | два письма, два договора | `processed_events`, уникальность `loan_documents (application_id, type)` |
| Relay на нескольких инстансах | двойная отправка | `FOR UPDATE SKIP LOCKED` |
| RabbitMQ долго недоступен | outbox растёт, письма задерживаются | события не теряются, relay дошлёт; `ERROR` после max-attempts |
| Таблица outbox разрастается | медленный relay | частичный индекс, очистка отправленных |
| Уведомление об одобрении раньше PDF | ссылка на договор даёт 404 | уведомление по `loan.contract.ready` (§4.5) |
| PDF в GridFS сохранён, а Postgres откатился | файл-сирота | детерминированное имя файла, перезапись при повторе (§4.8) |
| Blob тянется в списках | мегабайты на строку, медленная админка | отдельная сущность `KycDocument`, в списках только метаданные |
| `@Lob byte[]` в Hibernate на PostgreSQL | маппится в `oid` (large objects), мусор в БД | `byte[]` + `@JdbcTypeCode(SqlTypes.VARBINARY)` → `bytea`, **без `@Lob`** |
| Лимит тела запроса nginx — 1 МБ по умолчанию | загрузка паспорта падает с `413` до бэка | `client_max_body_size 6m` в `frontend/nginx.conf` |
| Лимит multipart Spring — 1 МБ по умолчанию | то же на стороне бэка | `spring.servlet.multipart.max-file-size: 5MB`, `max-request-size: 6MB` в `application.yml` |
| Подмена файла (не картинка) | мусор или вредный файл в БД | проверка сигнатуры, лимит размера |
| В фото есть EXIF с геолокацией | лишние персональные данные | в первой версии не вырезаем: фото видит только админ, просмотры журналируются, удаляется по §3.11 |
| Очистка удалила фото живой заявки | админ не видит паспорт | удалять только без ссылок из `SUBMITTED`/`APPROVED`/`ACTIVE`/`REPAID` (§3.11) |
| Перебор кода подписи или телефона | подпись без владельца телефона | 3 попытки, TTL 5 мин, пауза 60 с, код привязан к заявке и хэшу договора |
| Клиент сменил телефон после подтверждения | код уходит на неподтверждённый номер | смена номера сбрасывает `phone_verified_at` |
| Договор перегенерировали после отправки кода | подписан не тот документ | код и подпись привязаны к SHA-256 договора |
| Клиент поменял профиль после подачи | админ видит не те данные | снимок заявителя (§3.6) |
| Рабочие дни считаются в UTC | срок истекает на день раньше или позже | расчёт в `app.loan.business-zone`, хранение в `Instant` |
| Задачи по расписанию на нескольких инстансах | двойная обработка | истечение: строки берутся `FOR UPDATE SKIP LOCKED`, для каждой переход + `loan_events` + outbox в одной транзакции; очистка KYC — одним условным `UPDATE` |
| Клиент поменял зарплату в профиле | старые заявки показывают новую зарплату | зарплата копируется в снимок заявки (§3.6) |
| Админ забыл отметить погашение | клиент не может подать новую заявку | займы в `ACTIVE` после срока возврата видны админу в списке с фильтром по статусу `ACTIVE` |
| Зарплата 0 или отрицательная | деление на ноль в ПДН | валидация `monthlyIncome > 0` и `CHECK` в БД |
| Изменение в Postgres есть, в Mongo нет | кредитная история отстаёт | outbox + `credit_history_synced_event_id` + сверка (§4.9) |
| Повторная или поздняя запись в Mongo | дубль или откат к старому состоянию | `_id = applicationId`, полная замена с условием `lastEventId $lt` (§4.9) |
| Модификатор поменяли после подачи | у заявки меняется сумма к возврату | модификатор в снимке условий (§3.6) |
| Кто-то пишет в `credit_history` в обход consumer-а | расхождение с Postgres | единственный писатель, пересборка из Postgres |
| История клиента грузится N+1 | медленная карточка | один запрос с join `loan_applications` + `loan_types`, сводка одним `GROUP BY` |
| Деньги в `double` | центы теряются | только `BigDecimal`, в JSON строки |

## 7. Конвенции и паттерны

### 7.1 Общие
Всё из `INSTRUCTION.md` §4 обязательно:
- слои `web → service → repository`;
- DTO — `record`;
- сущности не выходят из контроллеров;
- модули не ходят в чужие репозитории.

### 7.2 Состояние заявки — только через методы сущности
- Нет публичного `setStatus`. Есть `approve(adminId, comment, clock)`, `reject(adminId, reason, clock)`,
  `cancel(clock)`, `activate(signature, clock)`, `expire(clock)`.
- Допустимые переходы описаны в одном месте: `LoanStatus.canTransitionTo(target)`, таблица из §3.8.
- Недопустимый переход → `InvalidStatusTransitionException` → `409`.

### 7.3 Снимки — value objects
- `LoanTerms` (ставка, проценты, сумма к возврату) и `ApplicantSnapshot` (ФИО, телефон, KYC) — `@Embeddable`.
- Создаются один раз при подаче, сеттеров нет.

### 7.4 Внешние зависимости — через порты
- `SolvencyCheck`: на вход заявка, на выход подсказка для админа. Сейчас одна реализация `DebtLoadCheck`
  (ПДН на лету, ничего не пишет). Позже бюро и скоринг добавятся списком бинов `SolvencyCheck`.
- `CreditHistoryStore`: запись и чтение кредитной истории. Реализация на Mongo. Запись — только из consumer-а и пересборки.
- `SmsClient`: HTTP-клиент отдельного `sms-verification-service`, собственного SMS-провайдера в бэкенде нет.
  - Адрес — `SMS_CLIENT_BASE_URL` (по умолчанию `http://sms-verification-service:8091`), вызовы подписаны
    service-to-service JWT (`SMS_CLIENT_SERVICE_JWT_SECRET`, по умолчанию `JWT_SECRET`).
  - Провайдер выбирается в самом сервисе: `SMS_VERIFY_PROVIDER` = `sim` | `vonage` | `twilio`
    (`VONAGE_API_KEY`, `VONAGE_API_SECRET`, `VONAGE_FROM` / `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_SECRET`, `TWILIO_FROM`).
    На trial-аккаунте Twilio SMS уходят только на номера из Verified Caller IDs.
  - На каждый запрос кода генерируется новый `Idempotency-Key`; повторный запрос — не чаще раза в 60 секунд.
    Раньше — `CodeCooldownException` → `429 RATE_LIMITED` (и для телефона, и для подписи).
  - Ответ сервиса `429` → `429 RATE_LIMITED`; недоступность или `5xx` → `502 SMS_DELIVERY_FAILED`.
    После неудачной отправки ключ cooldown снимается, клиент может повторить сразу.
  - Ключи Redis: `phone-verification:<userId>:<uuid>` и `signing:<applicationId>:<uuid>`; cooldown —
    `phone-otp-cooldown:<userId>` и `sign-otp:cooldown:<userId>`.
  - nginx не проксирует `/api/v1/sms`: снаружи доступен только бэкенд.
- `ContractRenderer`: PDF договора из снимка. Шаблон отдельно от кода.

### 7.5 Чистые функции
- `LoanQuoteCalculator` без Spring и IO, как `calculator`. Используется и в `/quote`, и при подаче:
  сумма в заявке пересчитывается на сервере, клиенту не доверяем.
- `BusinessDays.plus(instant, days, zone)`, `DebtLoad.percent(total, income)` и `CreditHistoryAssembler`
  (заявка + `loan_events` → документ) — тоже чистые функции.

### 7.6 Транзакции и события
- Одна бизнес-операция — одна транзакция в сервисе (`@Transactional` на методе сервиса, не на контроллере).
- События только через `OutboxPublisher` внутри этой транзакции (§4.8).
- Каждый consumer начинается с проверки `processed_events`.
- Внешние вызовы (SMS, генерация PDF, запись в Mongo) не держат транзакцию Postgres открытой: сначала внешний вызов, потом короткая транзакция.
- Каждое действие с заявкой пишет строку в `loan_events` и событие `loan.history.changed` в outbox в той же транзакции.
  Неверный код подписи пишется короткой отдельной транзакцией.
- Строка в `loan_events` без `loan.history.changed` — ошибка: Mongo не узнает об изменении до сверки.
  Поэтому оба пишутся одним методом `LoanEventRecorder.record(...)`.

### 7.7 Конкурентность
- `@Version` на `loan_types`, `loan_applications`, `customer_profile`.
- Отметка «Погашен» тоже передаёт `version`: два админа не закроют один заём дважды.
- Уникальность активной заявки — индексом в БД. Проверка в коде нужна только для понятной ошибки.

### 7.8 Время и настройки
- `Clock` внедряется, `Instant.now()` напрямую не вызывать.
- Все лимиты в `application.yml`:
  - `app.loan.*` — срок предложения, часовой пояс, параметры кодов, порог ПДН;
  - `app.kyc.*` — размер файла, разрешённые типы, срок хранения;
  - `app.outbox.*` — интервал, размер батча, максимум попыток, срок хранения;
  - `app.credit-history.*` — интервал сверки, задержка перед сверкой.

### 7.9 Миграции
- Одна миграция на логический шаг, только вперёд.
- Таблицы во множественном числе, `snake_case`. Деньги `numeric(12,2)`, ставки `numeric(6,3)`.

### 7.10 Фронт
- Все запросы через `frontend/src/api/` (`types.ts`, `http.ts`, `mock.ts`).
- Новый эндпоинт → метод в `Api`, реализация в `http.ts` и мок в `mock.ts`.
- Деньги приходят строками, форматируются в `BYN` только при выводе.

### 7.11 Комментарии в коде
Комментарий объясняет **что делает код и зачем он так сделан**, если это не видно из имён.
Пересказывать код словами не нужно.

**Обязательно комментировать:**
- **Назначение класса.** Короткий javadoc у публичных классов модулей `customer`, `loan`, `common.outbox`:
  за что класс отвечает и где его место во флоу.
- **Неочевидные решения**, особенно те, что легко «упростить» и сломать:
  - снимок условий и данных в заявке — зачем копируем, а не ссылаемся;
  - частичный уникальный индекс одного активного займа — почему проверка в базе, а не только в коде;
  - `byte[]` + `@JdbcTypeCode(SqlTypes.VARBINARY)` без `@Lob` — чтобы не получить `oid`;
  - outbox и `Propagation.MANDATORY` — почему событие нельзя отправлять напрямую;
  - полная пересборка документа в Mongo и условие `lastEventId $lt` — почему нельзя `$set` и `$push`;
  - порядок шагов там, где транзакция не покрывает всё: GridFS, Redis, Mongo;
  - уведомление об одобрении только после готовности PDF;
  - `404` вместо `403` для чужой заявки.
- **Бизнес-правила с цифрами:** откуда 7–30 дней, 5 рабочих дней, 3 попытки кода, порог ПДН 50 %, 7 дней хранения фото.
  Сами значения живут в `application.yml`, в комментарии — смысл правила.
- **Обходы и ограничения:** почему здесь так, что сломается, если убрать.

**Не нужно комментировать:**
- то, что понятно из имени метода или переменной (`// сохраняем заявку` над `repository.save(application)`);
- геттеры, конструкторы, простые DTO и мапперы;
- историю изменений («раньше было так») — для этого есть git;
- закомментированный код — его удаляют.

**Как писать:**
- По-русски, коротко: одна-две строки. Если нужен абзац, значит место сложное и, скорее всего, его стоит упростить.
- «Зачем» важнее «что»: `// Снимок: админ меняет ставку типа, а договор должен остаться на условиях подачи.`
- Комментарий меняется вместе с кодом. Устаревший комментарий хуже отсутствующего, ревьюер это проверяет.
- Ссылка на раздел этого документа там, где правило подробно описано: `// см. MICROLOANS.md §4.9`.

## 8. Тесты

**UNIT:**
- калькулятор: эталон из §3.2 (с модификатором), модификатор 0, границы 7 и 30 дней, ставка 0, округление;
- все пары статусов из §3.8, параметризованный тест;
- ПДН: обычный случай, округление, порог предупреждения, зарплата 0 отклоняется валидацией;
- `CreditHistoryAssembler`: хронология и проколы собираются из `loan_events` правильно;
- `BusinessDays`: понедельник + 5 → понедельник; пятница + 5 → пятница; суббота + 5 → пятница; граница суток в `Europe/Minsk`;
- валидация типа займа;
- проверка сигнатуры файла.

**IT (Testcontainers):**
- подача при неполном профиле или без KYC — нужные коды ошибок;
- два параллельных запроса на подачу → одна заявка;
- есть заём в `ACTIVE` → новая заявка `409 ACTIVE_APPLICATION_EXISTS`;
- при подаче зарплата из профиля копируется в снимок; смена зарплаты в профиле не меняет старую заявку;
- история: клиент видит только свои заявки с ПДН; сводка админа считает статусы и проколы верно;
- подача после удаления фото паспорта → `KYC_REQUIRED`;
- два параллельных решения админа → один `409`;
- чужая заявка и чужой документ → `404`;
- загрузка файла: больше лимита, не картинка, нормальный файл;
- подпись без подтверждённого телефона → `409 PHONE_NOT_VERIFIED`;
- полный путь: подача → одобрение → PDF → уведомление → код → `ACTIVE`, есть запись подписи;
- неверный код 3 раза → код сгорел;
- истечение предложения через 5 рабочих дней (через подменённый `Clock`);
- отметка «Погашен»: `ACTIVE → REPAID`, после неё можно подать новую заявку; из других статусов → `409`;
- **кредитная история (Testcontainers Postgres + Mongo + RabbitMQ):**
  - каждая смена статуса и каждый прокол → документ в Mongo совпадает с Postgres, `credit_history_synced_event_id` равен последнему event;
  - полный путь `SUBMITTED → APPROVED → ACTIVE → REPAID` → в документе вся хронология;
  - повторная доставка → один документ;
  - старое событие после нового → документ не откатывается;
  - Mongo недоступна → отметка отстаёт, после восстановления сверка догоняет;
  - падение между записью в Mongo и отметкой в Postgres → после повтора документ и отметка согласованы;
  - пересборка после удаления коллекции → все заявки на месте;
- **outbox:**
  - откат транзакции → строки в outbox нет;
  - relay отправляет и помечает `published_at`;
  - RabbitMQ недоступен → строка остаётся, после восстановления уходит;
  - повторная доставка → одно уведомление и один договор;
- очистка KYC: удаляется через 7 дней после отказа, не удаляется при живой заявке;
- блокировка пользователя: refresh не работает, заявку подать нельзя;
- список админа не загружает содержимое KYC.

## 9. Порядок реализации

Каждый шаг — отдельный PR, бэк и фронт вместе:
1. **Outbox:** `outbox_events`, `processed_events`, `OutboxPublisher`, relay, очистка. Без бизнес-событий, с тестами.
2. **Профиль клиента:** `customer_profile`, `GET/PUT /api/me/profile`, раздел «Профиль» в личном кабинете.
3. **Подтверждение телефона:** `sms-verification-service` (SMS + OTP в Redis), backend ходит в него по HTTP; cooldown 60 с.
4. **KYC:** `kyc_documents`, загрузка, лимиты nginx и Spring.
5. **Типы займов:** админский CRUD, seed-миграция, публичный список, калькулятор `/quote`.
6. **Подача заявки** со снимком зарплаты и модификатора, журналом `loan_events` (`LoanEventRecorder`), разделы «Мои займы» и «Карточка займа» в личном кабинете.
7. **Панель заявок админа:** список, карточка со сводкой клиента, просмотр паспорта с журналом, одобрение и отклонение, уведомления и письма.
8. **Договор PDF** в GridFS и скачивание.
9. **Подпись** кодом из SMS → `ACTIVE`; отметка админа «Погашен» → `REPAID`.
10. **Задачи по расписанию:** истечение предложений и очистка KYC.
11. **Кредитная история:** consumer `loan.credit-history.q`, сверка, пересборка, сводка и просмотр в админке.
12. **Панель пользователей:** список, карточка с историей и кредитной историей, блокировка.

| Вопрос | Решение |
|---|---|
| Что после подписи | статус `ACTIVE`; админ вручную отмечает «Погашен» → `REPAID`; платежей и просрочки нет |
| Проценты | простые дневные от суммы займа, без неустоек |
| Модификатор | фиксированная надбавка типа в BYN, задаёт админ, прибавляется к сумме к возврату, в снимке заявки |
| Типы на старте | «На iPhone» (модификатор 150 BYN) и «До зарплаты» |
| Валюта | BYN, одна на систему |
| Телефон | подтверждается в форме, обязателен для подписи, не для подачи |
| Причина отказа | клиент видит в ЛК, в письме её нет |
| Срок предложения | 5 рабочих дней, пн–пт, `Europe/Minsk`, без праздников |
| Активные займы | не больше одного на пользователя (`SUBMITTED`, `APPROVED`, `ACTIVE`) |
| Зарплата | в профиле клиента, копируется в снимок заявки |
| Платёжеспособность | ПДН = сумма к возврату / зарплата из снимка, считается на лету, не хранится; порог предупреждения 50 %, решение за админом |
| Хранилища | Postgres — источник правды, все операции и статусы; Mongo `credit_history` — копия всех состояний всех займов с проколами |
| Согласованность | outbox, единственный писатель, полная пересборка документа из Postgres, версия `lastEventId`, отметка в Postgres, сверка, пересборка коллекции (§4.9) |
| История | клиенту — из Postgres; админу — кредитная история из Mongo |
| История микрозаймов | клиенту — своя, админу — со сводкой на карточке заявки и пользователя |
| Фото паспорта | один файл главного разворота, JPEG/PNG до 5 МБ, в Postgres отдельной таблицей, EXIF не вырезаем |
| Хранение фото | удаляется через 7 дней после отказа, отмены или истечения, если на него не ссылается живой или подписанный займ; метаданные остаются |
| Просмотры паспорта | строка в логе приложения, отдельной таблицы нет |
| Договоры | PDF в GridFS |
| Подпись | код из SMS, юридически достаточно |
| SMS-провайдер | отдельный `sms-verification-service`; провайдер `sim` / `vonage` / `twilio` (`SMS_VERIFY_PROVIDER`), backend только вызывает сервис по HTTP |
| Личный кабинет | профиль, мои займы, карточка займа, уведомления (§3.13) |
| Комментарии в коде | что и зачем для неочевидных решений и бизнес-правил, без пересказа кода (§7.11) |
| События | своя таблица outbox; старые модули переводятся отдельной задачей |
